What is Siphon?

Imagine you order a 200-page report from a supplier, but you only need three numbers from page 47. Today, most teams write custom code every time they need to pull specific data from an API response. That code is brittle, hard to maintain, and impossible for non-engineers to read.

Siphon replaces that throwaway code with a simple recipe. You write a short description of what data you want (called a "spec"), and Siphon extracts it for you. Think of it like a mail-merge template, but for JSON APIs instead of Word documents.

The spec is just data -- a small YAML or JSON file that anyone on the team can read, version-control, and change without touching application code. When the API response structure changes, you update the spec, not the codebase.

The analogy: Just as a physical siphon draws liquid from a container through a tube, Siphon draws the exact data you need from nested JSON structures -- define the path, and let it flow.

Step by Step

  1. Define paths -- tell Siphon where your data lives using dot-notation (e.g., $.orders[*].total).
  2. Add filters (optional) -- narrow results with conditions like "status equals active" or "price greater than 50".
  3. Project fields (optional) -- rename and reshape the output so downstream systems get a clean, consistent schema.
  4. Call one function -- pass your spec and data to process(), query(), or pipeline(). Done.

Feature Overview

Siphon offers three progressively powerful APIs. Each builds on the one below.

Simple Extraction

The process() API is the quickest way to pull fields from a JSON response. Define paths, optional filters, and optional field renaming -- all in a plain dictionary.

When to use it: You need to grab a few specific fields from an API response, optionally filter an array, or aggregate values (find the minimum, maximum, sum, count, etc.) without writing post-processing code.

Raw API Response
{ "data": { "id": "prod_123", "items": [ {"id": 1, "status": "active", "name": "Widget"}, {"id": 2, "status": "inactive", "name": "Gadget"}, {"id": 3, "status": "active", "name": "Thing"} ] } }
Extracted Output
{ "id": "prod_123", "active_items": [ {"item_id": 1, "item_name": "Widget"}, {"item_id": 3, "item_name": "Thing"} ] }
The spec that does this
spec = { "extract": { "id": "$.data.id", "active_items": { "path": "$.data.items[*]", "where": {"status": "active"}, "select": {"item_id": "id", "item_name": "name"}, "collect": True } } } result = process(spec, data)

Advanced Querying

The query() API adds hierarchical chaining, MongoDB-style filter operators (greater-than, regex, in-list, etc.), sorting, pagination, and parent-to-child field carry-forward.

When to use it: You need complex filtering logic, sorted results, pagination, or multi-level nested extraction.

Complex Nested Data
{ "orders": [ {"id": 1, "status": "shipped", "total": 99.99}, {"id": 2, "status": "pending", "total": 149.99}, {"id": 3, "status": "shipped", "total": 29.99} ] }
Filtered, Sorted Output
[ {"order_id": 3, "amount": 29.99}, {"order_id": 1, "amount": 99.99} ]
The spec that does this
spec = { "from": "$.orders[*]", "where": {"status": "shipped"}, "select": {"order_id": "id", "amount": "total"}, "sort": [{"field": "total", "order": "asc"}], "collect": True } result = query(spec, data)

Multi-Stage Pipelines

The pipeline() API lets you run multiple named stages that can reference each other's output. This enables joins across sibling arrays -- like SQL joins but for JSON.

When to use it: You need to cross-reference data between separate arrays in the same API response (e.g., match rates to start times in a booking API).

Example: join rates to start times
stages = [ { "id": "rate", "from": "$.rates[*]", "where": {"id": 1}, "select": {"startTimeIds": "startTimeIds"} }, { "from": "$.startTimes[*]", "where": { "id": {"$in": "$stages.rate.startTimeIds"} }, "collect": True, "select": {"hour": "hour", "minute": "minute"} } ] result = pipeline(stages, data)

Stage 1 finds a rate and captures its startTimeIds. Stage 2 uses that list to filter the start times array. The result is only the start times matching the selected rate.

Pipeline Visualization

A pipeline is a sequence of named stages. Each stage reads from the original data and can reference the output of any earlier stage. Here is how a three-stage pipeline flows:

1
Stage: find_rate
Filter $.rates[*] to find the rate matching id=1. Select its startTimeIds list.
2
Stage: find_times
Filter $.startTimes[*] where id is in the rate's time list.
$stages.find_rate.startTimeIds
3
Stage: final_output
Project and format the matched start times into the final output shape for the application.
$stages.find_times.hour

Key behaviors of pipelines:

  • Every stage reads from the original root data, not from the previous stage's output.
  • Stages reference earlier outputs using the $stages.<id>.<field> syntax in their where clauses.
  • The last stage's output becomes the pipeline's return value.
  • Stages without an id still execute but cannot be referenced by later stages.

Quick Start

Get up and running in under two minutes.

1. Install

pip install siphon-dsl

2. Write a spec

from siphon import process data = { "users": [ {"name": "Alice", "role": "admin", "active": True}, {"name": "Bob", "role": "viewer", "active": False}, {"name": "Carol", "role": "admin", "active": True}, ] } spec = { "extract": { "active_admins": { "path": "$.users[*]", "where": {"role": "admin", "active": True}, "select": {"name": "name"}, "collect": True } } } result = process(spec, data) # {"active_admins": [{"name": "Alice"}, {"name": "Carol"}]}

3. Optional extras

# For fetching from live APIs: pip install siphon-dsl[http] # For Pydantic-validated specs: pip install siphon-dsl[typed]

4. Use the advanced APIs (optional)

# Chaining query with MongoDB-style filters from siphon import query result = query({ "from": "$.users[*]", "where": {"role": {"$ne": "viewer"}}, "sort": [{"field": "name", "order": "asc"}], "collect": True }, data) # Multi-stage pipeline from siphon import pipeline result = pipeline([ {"id": "admins", "from": "$.users[*]", "where": {"role": "admin"}, "collect": True, "select": {"name": "name"}}, {"from": "$.users[*]", "where": {"name": {"$in": "$stages.admins.name"}}, "collect": True} ], data)

Glossary

Spec
A declarative description of what data to extract. Written as a YAML or JSON dictionary. Analogous to a SQL query but for JSON.
Path
A dot-notation string that describes where data lives in a JSON structure. Example: $.data.items[*].name
[*] (Star Notation)
A marker in a path that means "iterate over every item in this array." Siphon processes each element and applies filters/projections to each one.
Where (Filter)
A set of conditions that items must match to be included in the output. Supports simple equality and MongoDB-style operators like $gt, $in, $regex.
Select (Projection)
A mapping that renames and reshapes output fields. Example: {"cost": "pricing.amount"} extracts the nested amount field and renames it to "cost".
Collect
A flag that controls whether Siphon returns just the first match (default) or all matches as a list.
Reduce
An aggregation operator that collapses an array of values into a single result -- the minimum, maximum, sum, count, first occurrence, last occurrence, a joined string, or a deduplicated list. Declared directly in the spec; no post-processing code needed.
Pipeline
A sequence of named extraction stages that run against the same root data. Later stages can reference earlier stages' output, enabling cross-array joins.
Carry-Forward
When using chained queries with "then", parent-level fields are automatically merged into child results. This means child items inherit context from their parents.
Ancestor Filtering
The ability to filter deeply nested items by properties that belong to their parent or grandparent levels. For example, filtering passengers by their parent rate's ID.
DSL (Domain-Specific Language)
A small, focused language designed for one specific task. Siphon's DSL is the spec format -- a mini-language for describing JSON data extraction.
