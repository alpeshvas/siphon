# Siphon Spec v0.12

Extends the **pipeline** API (multi-stage `stages`) with two capabilities that together let a single spec combine root-level scalars with fields joined from sibling arrays:

1. **Root-capture stage** — `from: "$"` yields the root document as a single-item iteration, so a stage can project top-level scalars into the stages context.
2. **`$stages.<id>.<field>` references in `select`** — previously honored only in `where`, these references can now appear as `select` values and are carried through as literal values (not paths).

## Overview

Pipelines in v0.11 returned only the last stage's output, and prior-stage references (`$stages.<id>.<field>`) resolved only inside `where`. That made the natural pattern of "look up a joined sub-array entry, then return it alongside some root-level scalars" impossible to express in a single spec — the join stage's `select` had no way to pull in fields that lived outside its `from` array.

v0.12 closes that gap with two minimal additions. No syntax changes to existing specs; both features are opt-in.

---

## Root-Capture Stage

`resolve_from("$", data)` returns `[data]` when `data` is not already a list. The stage iterates once over the root document, so its `select` projects fields by relative path against the root.

```python
{
    "id": "activity",
    "from": "$",
    "select": {
        "bookingType": "bookingType",
        "bookingCutoffHours": "bookingCutoffHours",
        "hasOpeningHours": "hasOpeningHours",
    }
}
```

Stage output (with `collect` unset, terminal level returns the single match):
```json
{"bookingType": "DATE_AND_TIME", "bookingCutoffHours": 24, "hasOpeningHours": false}
```

`from: "$"` is distinct from an absent `from` (which on a dict yields `[]`) and from `from: "$.someArray"` (which iterates that array).

## `$stages` References in `select`

`pipeline()` applies `resolve_select_refs()` per stage. Any `select` value whose string is exactly `"$stages.<id>.<field>"` is replaced with a literal-value marker `{"$literal": <resolved value>}` before the stage runs. `project()` honors the marker and returns the literal directly without path resolution.

Why a marker (and not direct substitution)? If we simply substituted the resolved value into the `select` map, a downstream `project()` call would still treat the value as a path string and try to traverse it on the iterated item — silently returning `None` whenever the literal didn't happen to also be a valid path on the item. The `$literal` marker makes "this is a value, not a path" explicit.

```python
{
    "from": "$.startTimes[*]",
    "where": {"id": "$stages.rate.firstStartTimeId"},
    "select": {
        "hour": "hour",
        "minute": "minute",
        "bookingType": "$stages.activity.bookingType",   # carried from prior stage
    }
}
```

Only **whole-value** substitution is supported — a `select` string `"foo || $stages.x.y"` is not resolved as a coalesce mixing literals and paths; the entire value must be the `$stages.<id>.<field>` form to be treated as a literal reference.

## Combined Example

Data with sibling arrays linked by a foreign key, plus root scalars:

```python
data = {
    "bookingType": "DATE_AND_TIME",
    "bookingCutoffHours": 24,
    "rates": [{"id": 1, "startTimeIds": [10]}],
    "startTimes": [{"id": 10, "hour": 9, "minute": 0, "duration": 4}],
}
```

Single unified spec returning a flat dict of joined startTime fields + carried root scalars:

```python
spec = {"stages": [
    {"id": "activity", "from": "$",
     "select": {"bookingType": "bookingType", "bookingCutoffHours": "bookingCutoffHours"}},
    {"id": "rate", "from": "$.rates[*]",
     "select": {"firstStartTimeId": "startTimeIds[0]"}},
    {"from": "$.startTimes[*]",
     "where": {"id": "$stages.rate.firstStartTimeId"},
     "select": {
         "hour": "hour", "minute": "minute", "duration": "duration",
         "bookingType": "$stages.activity.bookingType",
         "bookingCutoffHours": "$stages.activity.bookingCutoffHours",
     }},
]}
```

Result:
```json
{
  "hour": 9,
  "minute": 0,
  "duration": 4,
  "bookingType": "DATE_AND_TIME",
  "bookingCutoffHours": 24
}
```

## Behavior Reference

| Construct | Where it resolves | What it does |
|---|---|---|
| `from: "$"` | Stage `from` | Iterates root once (single-item list) so `select` can project root scalars |
| `$stages.<id>.<field>` in `where` | `where` value (existing, unchanged) | Substituted with prior-stage output's field value before filter evaluation |
| `$stages.<id>.<field>` in `select` | `select` value (new in v0.12) | Resolved to a `{"$literal": value}` marker; `project()` returns the literal as-is |
| `{"$literal": value}` in `select` | `project()` (new in v0.12) | Returns `value` directly without path lookup |

Edge cases:
- **Empty prior stage** — if the referenced stage produced `None`, `resolve_ref` returns `None` and the literal is `None`.
- **List prior stage** — if the referenced stage output is a list of dicts, `resolve_ref` returns a list of field values (existing behavior; same as in `where`).
- **Non-pipeline contexts** — `from: "$"` works in plain `query()` calls too (not pipeline-only). `$stages.<id>.<field>` references require pipeline context (there are no stages outside `pipeline()`).

## Changes from v0.11

- **`resolve_from`** — new special case: `from_path == "$"` returns `data` wrapped as a single-item list (when not already a list).
- **`pipeline()`** — now calls a new `resolve_select_refs()` helper alongside `resolve_refs()`, applying it to each stage's `select` before delegating to `query()`.
- **`project()`** — recognises `{"$literal": value}` source markers and returns the value directly, bypassing path resolution and coalesce handling.

Nothing about existing specs changes. Specs that don't use `from: "$"` or `$stages` references in `select` behave identically to v0.11.
